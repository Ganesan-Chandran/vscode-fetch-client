# Session 12: Model Providers and First Model API Call

## 1. Objective

Understand how an AI Agent communicates with an LLM provider and perform the first successful model API call.

The objective is to understand the model provider interaction before implementing the provider abstraction in TypeScript.

This session focuses on:

- Understanding different LLM providers.
- Comparing local and cloud model providers.
- Understanding Ollama's HTTP API.
- Making the first model API call.
- Examining the model response structure.
- Understanding how LLM responses can be used by the AI Agent.

**Architecture principle:** Build our own AI Agent using native TypeScript and HTTP APIs without depending on an external Agent SDK.

## 2. Model Provider Overview

An LLM provider exposes a model that an application can communicate with through an API.

Examples:

| Provider      | Model examples     | Hosting |
| ------------- | ------------------ | ------- |
| Ollama        | Qwen, Llama, Gemma | Local   |
| OpenAI        | GPT models         | Cloud   |
| Google Gemini | Gemini models      | Cloud   |
| Anthropic     | Claude models      | Cloud   |

Different providers may expose different API endpoints and response formats.

Our AI Agent should eventually communicate with different providers through a common application-level contract.

Provider abstraction and common request/response types are covered in the next session.

## 3. Why Ollama?

Ollama allows us to run LLMs locally and communicate with them using HTTP APIs.

Advantages:

1. Local model execution.
2. No requirement for a cloud API key.
3. Local HTTP API.
4. Support for multiple models.
5. Suitable for experimentation and development.
6. Allows us to test the AI Agent without recurring API costs.

Official documentation:

https://ollama.com/

API documentation:

https://docs.ollama.com/api

## 4. Ollama Environment

The local Ollama server exposes its API at:

```text
http://localhost:11434
```

Model used in this session:

```text
qwen2.5-coder:3b
```

API endpoint:

```text
POST http://localhost:11434/api/generate
```

The `/api/generate` endpoint generates a response based on the supplied prompt.

## 5. First Model API Call

Executed the following command using curl:

```bash
curl http://localhost:11434/api/generate -d '{
  "model": "qwen2.5-coder:3b",
  "prompt": "Return only JSON with keys \"method\" and \"url\" for: get the users list from https://api.example.com/users",
  "stream": false
}'
```

### Request explanation

| Property | Description                                                            |
| -------- | ---------------------------------------------------------------------- |
| model    | Specifies the model to execute                                         |
| prompt   | Contains the instruction sent to the model                             |
| stream   | `false` requests a single complete response instead of streamed chunks |

### API response

Ollama returned:

````json
{
  "model": "qwen2.5-coder:3b",
  "created_at": "2026-11-21T15:00:48.5786822Z",
  "response": "```json\n{\n  \"method\": \"GET\",\n  \"url\": \"https://api.example.com/users\"\n}\n```",
  "done": true,
  "done_reason": "stop"
}
````

The API call was successful.

## 6. Understanding the Response

The response contains several properties.

| Property          | Description                              |
| ----------------- | ---------------------------------------- |
| model             | Model used for generation                |
| created_at        | Response creation timestamp              |
| response          | Actual generated model content           |
| done              | Indicates generation has completed       |
| done_reason       | Reason generation stopped                |
| context           | Token context information                |
| total_duration    | Total generation duration in nanoseconds |
| load_duration     | Model loading duration                   |
| prompt_eval_count | Number of prompt tokens evaluated        |
| eval_count        | Number of generated tokens               |

The most important property for our AI Agent is:

```typescript
response;
```

It contains the actual content generated by the model.

Other properties provide metadata and execution information.

## 7. Important Observation: LLM Output Is Not Always Pure JSON

Although the prompt explicitly requested JSON only, the model returned JSON wrapped in Markdown code fences.

Actual generated content:

```json
{
  "method": "GET",
  "url": "https://api.example.com/users"
}
```

This demonstrates an important characteristic of LLMs:

**Prompt instructions do not guarantee that the model will always return the requested output format.**

Our application must not blindly assume that generated content is valid JSON.

Potential response scenarios include:

1. Valid raw JSON.
2. JSON wrapped in Markdown code fences.
3. JSON followed by explanatory text.
4. Malformed JSON.
5. Unexpected response structure.

These scenarios need to be considered when designing the response-processing pipeline.

## 8. How This Fits into Fetch Client AI Agent

The first model API call demonstrates the basic communication flow.

```text
User
  |
  v
AI Agent
  |
  v
LLM Provider
  |
  v
Ollama HTTP API
  |
  v
Qwen2.5-Coder Model
  |
  v
Generated Response
  |
  v
AI Agent
```

The generated response can eventually be processed into an application-level request definition.

For example:

```json
{
  "method": "GET",
  "url": "https://api.example.com/users"
}
```

This structure corresponds to the `AgentRequest` contract discussed in Session 08.

The response-processing pipeline will need to distinguish between:

- Provider response parsing.
- Model-generated content extraction.
- JSON parsing.
- Runtime schema validation.
- Security validation.

These are separate responsibilities.

## 9. Architecture Decisions

| Area                 | Decision                        |
| -------------------- | ------------------------------- |
| Agent framework      | Build our own                   |
| External Agent SDK   | Not required                    |
| Programming language | TypeScript                      |
| HTTP communication   | Native HTTP/fetch               |
| Local LLM provider   | Ollama                          |
| Model                | qwen2.5-coder:3b                |
| Initial API testing  | curl                            |
| Streaming            | Disabled for initial experiment |
| Runtime validation   | Zod, introduced in Session 08   |

### Why avoid an external Agent SDK?

Building our own agent helps us understand and control:

- Model communication.
- Provider abstraction.
- Request and response contracts.
- Tool execution.
- Agent orchestration.
- Validation.
- Security policies.

The objective is not to recreate every feature of an existing framework. It is to implement the capabilities Fetch Client actually needs.
